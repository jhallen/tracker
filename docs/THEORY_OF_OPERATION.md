# Theory of Operation

This document describes how the Greenhouse Maintenance Tracker works, so that
a developer (or Claude Code) can quickly resume work. Keep it current: when
you change behaviour, update the relevant section and the **Status / TODO**
list at the end.

## 1. Purpose and scope

Greenhouse staff use the app to report broken equipment and other maintenance
problems, and maintainers use it to work through them. It has to work well
on a phone in the greenhouse, which means taking photos and scanning
equipment barcodes, and it also has to work on a desktop.

## 2. Technology stack

| Layer | Choice | Notes |
|---|---|---|
| HTTP server | **Axum 0.8** on Tokio | Path params use the `/{id}` syntax |
| HTML | **Askama 0.16** | compile-time templates in `templates/`; auto-escaped; `|safe` used only for sanitised rich text |
| DB access | **Diesel 2.4** + r2d2 pool | `features = sqlite, r2d2, chrono, returning_clauses_for_sqlite_3_35` |
| Database | **SQLite**, bundled via `libsqlite3-sys/bundled` | WAL mode, `foreign_keys=ON`, `busy_timeout=5000` set per connection (`db.rs`) |
| Migrations | Diesel SQL migrations in `migrations/` | embedded in the binary (`embed_migrations!`) and runnable with the Diesel CLI |
| Passwords | Argon2id (`argon2` 0.5) | PHC strings in `users.password_hash` |
| OAuth | hand-rolled authorization-code + PKCE using `reqwest` 0.12 (rustls) | no oauth2 crate; see `auth/oauth.rs` |
| HTML sanitising | `ammonia` | `sanitize.rs` |
| Email | `lettre` 0.11 (async SMTP, rustls) | `mailer.rs`; logs instead of sending when `SMTP_HOST` is unset |
| Front-end | Plain HTML/CSS plus three vanilla JS files | no build step; every page works without JS |
| Barcodes | native `BarcodeDetector`, else vendored ZXing 0.21.3 | `static/scanner.js` |

The app has no SPA, no bundler and no Node dependency. The server renders
every page, and JavaScript only adds enhancements.

## 4. Data model

```
users(id, email UNIQUE lower-case, display_name, password_hash NULL, is_admin, created_at,
      email_verified_at NULL)
email_verifications(id, user_id→users, email, token_hash UNIQUE, created_at, expires_at, used_at NULL)
oauth_identities(id, user_id→users, provider, subject, email, created_at, UNIQUE(provider, subject))
sessions(id = sha256(cookie token) hex, user_id→users, created_at, expires_at)
issues(id, title, description_html, location, equipment_code, equipment_code_format,
       priority ∈ {low,normal,high,urgent}, state ∈ {open,closed,unassigned,assigned},
       submitter_id→users, assignee_id→users NULL, created_at, updated_at, closed_at NULL)
comments(id, issue_id→issues, author_id→users, kind ∈ {question,response,note,event}, body_html, created_at)
attachments(id, issue_id→issues, comment_id→comments NULL, uploader_id→users,
            original_name, stored_name UNIQUE, content_type, size_bytes, created_at)
```

* All timestamps are **UTC** `NaiveDateTime`. SQLite stores them as TEXT. The
  browser converts them to local time (see `Ts` in `views.rs` and `app.js`).
* `issues` has two foreign keys into `users`, so Diesel has no `joinable!` for
  it. Handlers load names separately with `user_names()` into a HashMap.
* Enumerated values are TEXT columns with SQL `CHECK` constraints. Rust
  validates them first, with `IssueState::parse`, `PRIORITIES` and
  `COMMENT_KINDS`.
* Photos live on disk at `UPLOAD_DIR/<uuid>.<ext>`. The database stores only
  metadata. An attachment with `comment_id = NULL` belongs to the issue's
  original submission.

## 5. Issue lifecycle

The four states the specification asks for:

| State | Meaning | Assignee |
|---|---|---|
| `unassigned` | New. Nobody is responsible yet (initial state when no assignee is chosen) | none (always cleared) |
| `assigned` | Someone is responsible but has not started | required |
| `open` | Work in progress, or reopened after closing | optional |
| `closed` | Resolved. `closed_at` is set | kept |

`routes/issues.rs::update` applies these rules:

1. If only the assignee changed (the state select was left alone), the state
   follows it: setting an assignee changes `unassigned` to `assigned`, and
   clearing the assignee changes `assigned` to `unassigned`.
2. An explicit change to `unassigned` clears the assignee.
3. `assigned` with no assignee is rejected with a message.
4. Entering `closed` sets `closed_at`, and leaving `closed` clears it.
5. Every change writes an `event` comment, such as "changed state from X to
   Y", so the conversation doubles as an audit trail.

The **Take** button (`POST /issues/{id}/take`) is available to any logged-in
user while the issue has no assignee and is not closed. It assigns the issue to
the current user and moves `unassigned` to `assigned`.

## 6. Permissions

| Action | Who |
|---|---|
| View dashboard, lists, any issue, photos | any logged-in user (the greenhouse team is trusted) |
| Create an issue | any logged-in user |
| Post to the conversation, change state/assignee/priority | the issue's **submitter**, **assignee**, or an **admin** (`can_participate`) |
| Take an unassigned issue | any logged-in user |
| Users page, grant/revoke admin | admins (you cannot demote yourself; demotion kills that user's sessions) |

The first user ever created becomes an admin (`auth::create_user`).

## 7. Conversation model

A conversation is the ordered list of `comments` for an issue. A person posts
a `question`, a `response` or a `note`, optionally with photos. The form
defaults to `response` for the assignee and `question` for everyone else.
`event` rows are written by the system.

The dashboard flags **"awaiting your reply"** on an issue when all of these
hold: the viewer is its submitter or assignee, it is not closed, and its latest
non-event comment is a `question` written by someone else (`to_rows()` in
`routes/issues.rs`).

## 8. Authentication

### Sessions
* On login a 256-bit random token is set in the `gt_session` cookie
  (HttpOnly, SameSite=Lax, Secure when `BASE_URL` is https, Max-Age =
  `SESSION_HOURS`).
* The database stores only **SHA-256(token)**, so a leaked database does not
  leak live sessions. Expired rows are purged opportunistically on every new
  login.
* `CurrentUser` is an Axum extractor that resolves the cookie to a `User`. If
  it cannot, it returns `AppError::LoginRequired`, which redirects to `/login`.
  `MaybeUser` is the optional version.

### CSRF
`auth::same_origin_guard` runs as middleware on every non-GET/HEAD/OPTIONS
request. It requires the `Origin` header (or the `Referer` as a fallback) to
match `Host`, or `X-Forwarded-Host` when behind a proxy. Combined with
SameSite=Lax cookies, this means the app needs no per-form token, which keeps
multipart forms and `fetch()` uploads simple. **Tests must send
`Origin: http://localhost` and `Host: localhost`.**

### Passwords
Passwords are hashed with Argon2id using default parameters and must be at
least 8 characters (`MIN_PASSWORD_LEN`). A failed login for an unknown email
still runs a hash, so response timing does not reveal which emails exist.

### OAuth / OIDC (`auth/oauth.rs`, `routes/auth.rs`)
1. `GET /auth/{p}/start[?link=1]` generates `state` and a PKCE verifier and
   stores `"{slug}.{state}.{verifier}.{mode}"` in the `gt_oauth` cookie
   (path `/auth`, 10 min). It then redirects to the provider with
   `code_challenge=S256(verifier)`.
2. `GET /auth/{p}/callback?code&state` checks the cookie and the `state`. It
   then POSTs the code to the token URL (sending `client_secret` and
   `code_verifier`), fetches the userinfo URL with the bearer token, and maps
   the result to an `ExternalProfile {subject, email, email_verified, name}`.
   GitHub gets an extra call to `/user/emails` to find the primary verified
   address.
3. `resolve_identity` then decides what happens:
   * If `(provider, subject)` is already known, it logs that user in.
   * In `link` mode while logged in, it attaches the identity to the current
     user. It refuses if the identity belongs to someone else.
   * If the email already belongs to a local user, it **refuses**. It never
     auto-links. The user logs in with the password and links from the
     Profile page.
   * Otherwise it creates the user and the identity in one transaction.
4. A user cannot unlink their last identity unless they have a password.

Providers are enabled from the environment (`OAuthProvider::from_env`):
Google, Microsoft (`MICROSOFT_TENANT`), GitHub, GitLab (`GITLAB_BASE_URL`),
Facebook, Discord, and generic OIDC (explicit URLs). To add a provider:
1. Add a `ProviderKind` variant and give it a slug, an env prefix and a
   default name.
2. Add its endpoints and scopes in `from_env`.
3. If its userinfo is not standard OIDC, add a profile mapping arm in
   `fetch_profile`.

Apple would also need a JWT client secret and `response_mode=form_post`, which
means a POST callback route, and that route has to be exempted from
`same_origin_guard` because Apple posts cross-site.

### Username and display name
The email address is the username: it is what people log in with, it is
unique, and it is stored lower-cased. `display_name` is free text that other
people see on issues and in conversations, and it can be changed on the
Profile page. There is no way to change the email address yet. If that is
added, it must clear `email_verified_at` and send a new link.

## 9. Rich text

`templates/_editor.html` contains a `<textarea>`. On the server it holds
whatever the user typed. `app.js` hides the textarea and shows a
`contenteditable` area with a toolbar driven by `document.execCommand`. On
every input the area's HTML is copied back into the textarea.

On the server, `sanitize::clean_rich_text` sanitises the input with
`ammonia`. It allows these tags: p, br, div, span, b, strong, i, em, u, s, ul,
ol, li, h3, h4, blockquote, code, pre, a and hr. Links may only use http,
https, mailto or tel, and get `rel="noopener noreferrer nofollow"`. Input that
contains no `<` is treated as plain text (the no-JS path) and escaped into
paragraphs. Only sanitised HTML is ever stored, and only stored HTML is
rendered with `|safe`.

## 10. Photos (mobile camera)

* `_photos.html` has two file inputs, both named `photos`. One has
  `capture="environment"` so a phone opens the camera directly. The other has
  no `capture` attribute, so it opens the photo library.
* Without JS, the form posts as normal multipart.
* With JS (`app.js`), chosen files are kept in an array and shown as
  removable thumbnails. When the form is submitted, the script:
  1. Shrinks each image to at most 1920 px on the long edge, as JPEG at
     quality 0.85, using `createImageBitmap` with
     `imageOrientation: "from-image"` and a canvas. This also converts HEIC
     on Safari.
  2. POSTs the form with `fetch()` and then follows `resp.url` (the server
     answers with a 303 redirect). If the response is not a redirect, it is an
     error page, and the script writes it into the document.

  `fetch()` drops URL fragments, so after a comment the server redirects to
  `/issues/{id}?posted={cid}#c{cid}`, and `app.js` scrolls to that comment
  and highlights it.
* On the server, `uploads::parse_multipart` checks each file's type by **magic
  bytes** (JPEG, PNG, GIF, WebP, HEIC) and ignores the client's content type.
  It enforces `MAX_UPLOAD_MB` per file and at most 10 files per post. The
  whole body is limited by `DefaultBodyLimit` (`MAX_REQUEST_MB`).
* Files are written to disk before the database transaction. If the
  transaction fails, they are deleted (`uploads::discard`).
* `GET /attachments/{id}` requires login and serves the file with its sniffed
  content type, `nosniff` and `private` caching.

## 11. Barcode scanning (`static/scanner.js`)

* Any button with `data-scan="<input selector>"` opens a `<dialog>` with a
  live camera view. `data-scan-format="<hidden input>"` receives the
  symbology, such as `ean_13` or `qr_code`, which is stored in
  `issues.equipment_code_format`.
* The scanner uses the browser's `BarcodeDetector` if it exists (Chrome/Edge
  on Android, macOS, ChromeOS). Otherwise it lazily loads the vendored
  **ZXing** library (`/static/vendor/zxing-library.min.js`), which provides
  `BrowserMultiFormatReader.decodeFromConstraints`. ZXing is the path used on
  iOS Safari and Firefox.
* Supported formats: QR, EAN-13/8, UPC-A/E, Code 128/39/93, Codabar, ITF,
  Data Matrix, PDF417 and Aztec.
* Live video needs a secure context (HTTPS or localhost). As a fallback, the
  dialog offers **"Use a photo instead"**, which decodes a still image. The
  code can always be typed by hand.
* On the New request form the scan control is a large dashed
  "Scan equipment barcode" button just below the title, because users missed
  the earlier small button. Photos are also checked: `app.js` fires a
  bubbling `photos:added` event when photos are attached, and `scanner.js`
  runs `decodeFile()` on each one. If a barcode is found and the equipment
  code is still empty, the field is filled in and labelled
  "Found in your photo as …". A code the user typed is never overwritten.
  Before decoding with ZXing, `decodeFile()` scales photos down to 1600 px:
  a 12 MP photo takes about 0.4 s in headless Chromium.
* The issue list's search box also has a Scan button, so a technician can
  scan a machine and see its history. Search matches title, location and
  equipment code. On an issue page, the equipment code links to that search.

## 12. Front-end conventions

* Layout is mobile-first (`static/app.css`). It uses CSS custom properties,
  automatic dark mode and 44 px touch targets. The dashboard and the list
  page show a floating "+" button on phones, defined in `{% block fab %}`.
  Other pages leave the block out so the button does not cover form buttons.
* Cards for issues come from `_issue_card.html`, which expects a loop
  variable named `i` of type `IssueRow`.
* Askama partials that need parameters, such as `_editor.html`, get them
  through `{% let %}` before the `{% include %}`.
* Timestamps are rendered as `<time class="ts" datetime="…Z">`. `app.js`
  turns them into local time, or relative time when the element has
  `data-relative`.

## 13. Testing

* `cargo test` runs `tests/flow.rs`, which drives the router in process
  through `tower::ServiceExt::oneshot` with a temporary SQLite file. It
  covers registration, login, the CSRF guard, issue creation with a photo and
  a barcode, sanitising, permissions, Take, the question/response flow and
  "awaiting reply", closing, search, image validation, the admin page and
  logout.
* `tests/verify.rs` covers the email-verification link: sending, throttled
  resend, a bad token, confirming while logged out, already verified, an
  expired link, and the status shown on the profile, dashboard and admin
  pages. It uses the in-memory mailer.
* `tests/oauth.rs` starts a mock OIDC provider on 127.0.0.1 and runs a full
  sign-up followed by a sign-in through `/auth/oidc/*`.
* To check the browser parts by hand, run the server and use a phone over
  HTTPS. During development, the editor, client-side resizing, ZXing photo
  decoding and the phone layout were checked with Playwright: Pixel 7
  emulation, an EAN-13 image and a JPEG.

## 14. Operations

* Migrations run automatically at startup (`AUTO_MIGRATE=true`). To run them
  by hand, use `greenhouse-tracker migrate` or `scripts/migrate.sh run`
  (which takes a backup first).
* To back up, copy the SQLite file safely (`sqlite3 db ".backup out.db"`)
  together with `UPLOAD_DIR`.
* Moving to PostgreSQL would require these changes:
  1. Switch the Diesel features to Postgres.
  2. Regenerate the migrations (the SQLite types used are standard; `BOOLEAN`
     and `TIMESTAMP` map directly).
  3. Change `SqliteConnection` to `PgConnection` and drop the SQLite PRAGMAs
     in `db.rs`.
  4. Change `Integer` primary keys to `SERIAL`.

  `diesel::MultiConnection` could support both databases at once if needed.

## 16. Email and address verification

### Mailer (`src/mailer.rs`)
`AppState.mailer` is built from `Config.mail` (`MailConfig`) and has three
variants:
- **`Smtp`**: a pooled `lettre::AsyncSmtpTransport`. `SMTP_SECURITY` is
  `starttls` (`starttls_relay`), `tls` (`relay`, implicit TLS) or `none`
  (`builder_dangerous`, for a local relay or Mailpit). Messages are sent as
  `multipart/alternative` with a plain-text and an HTML part.
- **`Log`**: used when `SMTP_HOST` is unset. The whole email is written to
  the log at INFO level, so development needs no mail server.
- **`Memory`**: used by `Config::for_tests()`. Tests read the captured
  messages with `state.mailer.sent()`.

`Mailer::send()` returns `Err(String)` when delivery fails, and callers
decide whether to show the error. To add a new kind of email, add
`templates/email/<name>.txt` and `.html` with Askama structs (see
`auth/verify.rs`) and call `state.mailer.send(OutgoingEmail{..})`.

### Verification flow (`src/auth/verify.rs`)
1. `send_verification(state, user_id)` runs in these cases:
   - after password sign-up;
   - after an OAuth sign-up where the provider did *not* confirm the
     address, for example Microsoft;
   - when the user presses **Resend** (`POST /profile/resend-verification`).

   It refuses if the user is already verified or if the last email was sent
   less than `RESEND_COOLDOWN_SECS` (60) ago. Otherwise it stores
   `sha256(token)` with `expires_at = now + 48h` and emails
   `<BASE_URL>/verify-email?token=<token>`. A failure at sign-up is only
   logged; a failure on Resend is shown to the user.
2. `GET /verify-email?token=` (`routes/auth.rs::verify_email`) calls
   `confirm()`. Login is **not** required, because people often open the
   email on another device. The outcomes are:
   - **Verified**: sets `users.email_verified_at` and the token's
     `used_at`;
   - **AlreadyVerified**;
   - **Expired**;
   - **Invalid**: unknown token, already used, or the account's email no
     longer matches the address the link was sent to.

   Older unexpired links stay valid until one of them is used.
3. If an OAuth provider reports `email_verified` at sign-up, the account is
   created verified. Linking a provider whose verified email equals the
   account's email also marks the account verified (`mark_verified`).

### Where the status shows
- **Profile:** a ✓ Verified / Not verified badge, an explanation and the
  Resend button. When SMTP is not configured, it also says that email
  delivery isn't set up yet.
- **Dashboard:** a reminder banner with a Resend button.
- **Admin Users page:** a *Verified* column.
- **Templates:** `Nav.email_verified` is available on every page.

### Enforcement
None: an unverified user can use every feature. **Future status-update
emails should be sent only to users with `email_verified_at IS NOT NULL`.**
